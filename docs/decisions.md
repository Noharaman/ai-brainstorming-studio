# Architecture Decisions

現在も有効な設計判断のみを記載する。撤回・置き換え済みの判断は含まない。
安全境界そのものの詳細は `safety-model.md` を参照。

---

## 利用者の既存CLI設定を正とする（Existing CLI Mode）

### 判断
各AI CLIの既存のログイン・モデル・provider・ローカル設定をそのまま使う。アプリは認証情報を読み書きせず、ログイン操作を代行せず、API keyや有料providerへ自動フォールバックしない。

### 理由
以前の設計では、課金経路をサブスクリプションに固定するため、CLIの設定を上書きし、環境変数を除去し、providerを固定していた。これは二重に間違っていた。

1. **利用者が意図して選んだ構成を黙って壊した。** Bedrock/Vertex経由で使っている利用者の設定を無効化し、原因も示さずに失敗させていた。
2. **保証できないことを保証しようとしていた。** アカウント側のcredits設定や上限は、アプリからは観測できない。

### 帰結
アプリは「認証・provider・接続先を変更しない」ことは保証する。**しかし、その実行がどう課金されるかは判定も保証もしない。** README にもその区別を明記する。

### 再考する条件
CLIベンダーが、実行前に課金経路を確認できるAPIを提供した場合。

## 安全性が未証明の機能は無効側に倒す（Fail closed）

### 判断
安全境界を実証できない機能は、動作していても停止する。「未検証だが動くので有効のまま」を選ばない。

### 適用結果
- 外部AI CLI 3枠すべて停止（hook / MCP を実行単位で無効化できることを実証できなかったため）
- AIによるファイル編集を停止（編集プロセスをOSレベルで隔離する手段がないため）
- 自動テスト実行を停止（AIが書き換えたコードをアプリの権限で実行することになるため）

### 理由
このアプリは他社製CLIを利用者のマシンで起動し、利用者のプロジェクトを読ませる。境界が曖昧なまま「たぶん大丈夫」で出荷すると、失敗したときに壊れるのは利用者のデータである。**機能が減ることは受け入れられるが、保証できない境界を保証と書くことは受け入れられない。**

### 再考する条件
`safety-model.md` の「再開条件」を満たすOSサンドボックスが実装できた時点。

## 権限は「オブジェクトの不在」で表す

### 判断
読み取り専用を `write=False` のようなフラグで表現しない。**書き込み権限は `WriteGrant` オブジェクトが存在する場合にのみ発生する。** 全コマンドビルダの既定引数は `grant=None` とし、それが読み取り専用を意味する。

### 理由
フラグ方式では、フラグを立て忘れた経路・フラグを知らない古いコードが、既定で書き込み可能になる。オブジェクト方式なら、grantの存在を知らないコードは**構造的に**権限を渡せない。

grantは `run_id` と `agent` の両方を保持し、使用箇所で両方を照合する。これにより、Implementerへ発行した権限が同一runのCritic/Verifierへ広がらず、前回runの権限が次のrunへ生き残らない。

### 再考する条件
なし。この方式は機能停止中も維持する。

## 議長AIの出力は表記揺れを許容して照合する

### 判断
LM Studioの回答から見出しを探すとき、文字列の厳密一致ではなく「許容表記の照合」を行う（`chair_output.py`）。日本語以外で返ってきた場合は1回だけ再依頼し、それでも駄目なら**破棄せず理由を添えて返す**。

### 理由
実測（8ケース×2モデル×2反復＝32回）で、モデルは同じ依頼に対して見出しの表記を毎回変えることが分かった（`意見が割れたこと` / `意見の相違` / `意見の対立`、装飾も `### 結論` / `**結論**` / `*   **結論**:`）。厳密一致では**正しい回答が丸ごと破棄され、定型文に差し替わっていた**。利用者にはその理由すら表示されなかった。

言語逸脱は16回中1回発生した。英語で正しい構造の回答は「言語の問題」であって「壊れた回答」ではないため、破棄せず返す方が利用者の役に立つ。

### 再考する条件
構造化出力（JSON schema等）をLM Studio側で安定して強制できるようになった場合。

## 秘密情報のredactionは書き込み境界で行う

### 判断
呼び出し側ごとに `redact()` を呼ぶのではなく、`WorkspaceManager` と `ChatRoomManager` の**書き込み境界**で一律に適用する。`chat_rooms.json` は保存直前にdict/listを再帰的に走査する。

### 理由
呼び出し箇所は十数か所あり、1つ忘れれば漏れる。実際、メッセージ本文だけをredactしていた時期に、**ルーム名（依頼文の先頭から生成される）経由で漏洩する経路**が残っていた。境界で行えば、後からフィールドを追加しても漏れない。

### 再考する条件
なし。

## GUIの自動化レベルは能力オブジェクトを単一の情報源とする

### 判断
レベルの意味を `AutomationCapabilities`（ラウンド数・プラン作成・書込可否・テスト実行）として保持し、**効果が発生する場所で必ずこのオブジェクトを参照する**。ラベル文字列から挙動を推測しない。

### 理由
以前は5段階のラベルを表示しながら、実際には3つの整数しか読んでいなかった。「4: 実装・テストまで」を選んでも、AI相談のラウンド数が変わるだけでファイルは一切変更されず、UIにその旨の表示もなかった。**ラベルが実態より進んだ約束をしていた。**

現在GUIが提供するのは「相談のみ」「実装案まで」の2段階のみ。実装レベルは定義を残すが、書き込みが停止している間はメニューに出さない — **何もしない選択肢を見せることが、この設計で除去したかった失敗そのものだからである。**

### 再考する条件
なし。
